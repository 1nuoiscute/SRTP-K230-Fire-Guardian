## 排除掉的路径和故障

1. 最初用全屏 OSD0 叠在仍运行的摄像头上，并直接禁用原 OSD3 识别框层。虽然测试页能显示，但原视觉仍持续送帧，串口出现 `sys_queue no space to push data`。此方法不能部署。
2. 保留 OSD3 消费、把它的全局透明度设为 0。10 秒探针没有队列错误，但用户现场确认仍能隐约看见摄像头，识别框很明显；按用户目视结果判为失败。
3. 改为退出视觉后独立初始化 VB/屏幕。第一次独立探针能显示 30 秒，退出后用户看到乱码；原因是独立程序退出时释放缓冲但未关闭仍在扫描的 VO。该探针只存放在测试路径，没有写开机程序。正式候选加入 `kd_mpi_vo_disable()`，手动试验实现“数据页启动 → 收到 q 退出 → 原厂视觉程序再次启动”，串口有 `DATA:` 状态行、原厂 `kd_mpi_vicap_start_stream`，没有 `queue`/`failed`/`Exception`。但**屏幕切换的实体 KEY2 全流程尚未由用户验收**。
4. 手动闭环测试曾先向原控制器发 `q`，随后直接在串口运行两个程序。测试结束停在 `msh`，所以用户按矩阵 KEY2 时是黑屏，原 KEY1 也暂时无效。这是收尾遗漏，不是 KEY1 程序被覆盖；随后已重启，恢复原 p1 控制器，原面板 ELF 哈希仍为 `6dd398c1deea0d99721b44066f71df1cfe5801815d88740d9071ffaaaf9f9c46`。
5. 为避免再停在 `msh`，候选控制器加入 `selftest_data` 自动走“视觉 → 数据 → 视觉”，结束后计划自动重启。串口日志显示原视觉启动/停止、数据页 `DATA:` 状态更新、数据页退出 status=0、第二次原视觉启动/停止，未记录 VO 队列错误；**但用户现场反馈测试期间“现在都是乱码”**。串口调用成功不能证明屏幕正确，此候选按目视结果判定失败，不写入 p1。收到反馈后立即通过 ADB 重启，原面板 ELF 哈希及小核桥进程正常；用户随后确认“已恢复正常”。

## 下一步验收门槛

1. 先只在电脑端查显示层与缓冲生命周期。当前本机 SDK 仅有 VO 静态库和调用样例，没有 VO 实现源码；不能凭串口成功就推断独立显示正确。
2. 找到可解释并消除乱码的方案后，先完成有界试验，再由用户目视确认矩阵 KEY2 进入数据页、摄像画面和蓝框完全消失、曲线更新、KEY2 返回视觉，重复两轮。测试结束必须恢复正式版。
3. 只有整个闭环和无乱码退出通过，才考虑把候选控制器写入 p1。现有原视觉 ELF 与 KModel 均不替换。长时间运行和真实报警事件接入另行验收。
