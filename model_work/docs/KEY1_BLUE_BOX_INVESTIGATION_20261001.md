# KEY1 蓝框覆盖参数区研究｜2026-10-01

用户明确的问题是“面板显示时识别蓝框压在参数面板上”，不是 KEY1 隐藏后残影。正式 KEY2 标签 board-key2-20260930 已固定；研究不更换其控制器、数据页、模型或 p1。

## 方案与依据

优先试显示叠加顺序：在原视觉持续运行并消费 OSD3 的条件下，将 OSD0 参数面板与 OSD3 识别图形的顺序交换。面板背景 BGRA 透明度实测全部 255；若框在 OSD3，面板就能遮住参数区域内的框，上方仍保留。只改变遮挡，不宣称真正缩放/分屏或检测区域已经裁剪。

本地 /home/k230/mpp_rtos_v06/kernel/lib/libvo.a 的 kd_vo_set_config_mix 反汇编显示混合顺序默认写 VO+0x3cc=0x3210、VO+0x950=0xba987654。kd_vo_osd_enable 的 OSD0/3 对应 VO+0x118 bit4/7，并在操作后写 VO+0x4=0x11 更新。board.h 给出 VO_BASE 0x90840000。用户开屏后真实读回与这些默认值一致，enable=0x92；试验只将高顺序改为 0xba984657，保留其他来源顺序。

官方 [VO API](https://www.kendryte.com/k230_rtos/en/v0.8/api_reference/mpp/display.html) 描述 OSD 叠加支持，具体旧固件兼容以本地库与实机读回为依据。用户反馈后的成功/失败不能由 API 文档替代。

旧数据页研究曾出现识别层透明度降低后蓝框仍明显的现象，因此也保留“独立硬件画框”的备选解释；不预设 OSD 调序一定解决。

## 实际已执行

首次板在线但显示寄存器全为 0xffffffff，拒绝进入写入试验；用户随后确认摄像头、面板和蓝框可见。只读前置验证 p1=5cd8667b…、默认混合顺序和 OSD0/3 同时启用。

工具 tools/probe_key1_mix_order.py 默认只读，要求唯一新输出文件；--apply 必须匹配冻结 KEY2 p1、两个默认顺序以及两个 OSD 启用位。板端 shell 自己计时并注册退出/信号 trap，60 秒后恢复；模式切换或关闭时若寄存器由驱动改变，则不覆盖驱动的新值。没有停止 OSD 消费、写 GPIO 或刷固件。

真实运行读回 APPLIED=0xBA984657，60 秒后 RESTORED=0xBA987654；前后 order-low/order-high/enable 完全一致。原视觉、面板继续运行。实屏反馈等待中，**不能宣称蓝框已修好**。本地完整命令/收据在 artifacts/key1_20261001_mix_probe；公开摘要见 [试验身份](../../docs/key1_mix_probe_20261001.json)。

同时只读记录 OSD3 尺寸寄存器=540×960、面板=536×348、OSD3 Y 显示区50–1009。这些是原视觉与面板的不同画布，不把 540 与 536 盲目等同。一次独立硬件框寄存器快照活跃数为0，未与蓝框出现时刻同步，所以仅是线索，不能证明永远没有硬件框。

## 原视觉静态调用核对（同日追加）

冻结原视觉 ec2caafd… 的两个提交帧调用位于 0x200001514、0x200002408；调用前均设置 a0=6。旧 SDK 的 kd_mpi_vo_chn_insert_frame 通道为 OSD 枚举值加3，因此通道6对应 OSD3。原视觉这条图形提交路径有直接证据；不再仅根据独立候选源码推测它的行为。

原视觉中也链接了 kd_mpi_vo_draw_frame 包装函数（0x2005142bc），但整份 SDK objdump 输出没有发现指向它的已解析跳转/分支，完整 ELF 内没有其64位地址字面量。两个 OSD 提交均指向 0x200514460，说明工具能找到实际显示调用。结合不同步的零活跃硬件框快照，**更支持 OSD 图形层解释，但不排除间接/动态调用**，也不把静态结果当成实屏修复成功。

最初自编2/4字节线性扫描发现 .text 内混入字符串，出现扩展指令样式，不能称为完整指令解码；该尝试的本地收据保留，公开结论以工具链 objdump 检查为准。最终工具 [check_key1_draw_path.py](../../tools/check_key1_draw_path.py) 默认只读，先校验原 ELF SHA，再流式读取反汇编，仅输出数字和身份，不发布原程序或完整反汇编。真实调用样例和“数据地址注释不能算调用”的检查通过；完整本地 ELF 实际检查通过，摘要见 [绘制路径身份](../../docs/key1_draw_path_20261001.json)。

## 根据结果决定下一步

若调序有效：将已验证的顺序设置封装到独立面板候选，面板退出前恢复，兼顾 KEY1 隐藏/再显示、KEY2 进入/返回、K1 总开关及重启。先新文件名短测、真实反馈、保存构建与回退，再考虑正式替换。

若无效：不继续靠高频清框与原视觉争抢缓冲区。先定位蓝框究竟是 OSD3 像素还是硬件 kd_mpi_vo_draw_frame；在确认的数据路径上裁剪 y≥参数区起点的图形。OSD 图形可研究保持原缓冲消费而限制显示区域；硬件框需在生产坐标的位置裁剪。取得/修复可维护视觉源码后，该步骤还可同时开放融合所需的框数据，但不能把现有未通过摄像兼容的源码直接替换正式视觉。

裁剪目标：面板显示时框不能覆盖参数区，隐藏时恢复全屏框；原始检测结果保持完整供事件判断。两种显示方式都需与场景帧对照，不能用“完全关掉所有识别框”作为用户要求的完成状态。
