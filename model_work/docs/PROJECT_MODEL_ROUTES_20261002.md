## 同帧视频比较

新工具`eval_project_model_videos.py`对9段既有开发视频各解码一次，将同一采样帧依次交给全部5个模型。固定640、FP32、GPU0、rect=True、conf=.25、NMS IoU=.6、1fps；共307个共享采样画面、1535次模型推理。模型与视频前后哈希一致，解码帧数与视频元数据核对通过。保存逐帧预测及解码像素哈希；每段预先固定起/中/末三帧，全部9页、27个源画面实际查看。

有框数量不等于正确识别。视频8的三个复核画面里，v13框住贴纸，v14框住锅底蓝焰；因此两者43/43并不代表能力相同。视频7起/中两帧v14能定位火焰，v13和v15未检出；v14的第一帧有分开的火焰局部框。视频9三帧v14均定位火焰，v13起/末框贴纸、中间无框。v15 last也改善视频9，但起/末仍多贴纸框。演示不放贴纸，贴纸错误作为附加边界保留。

视频7的最长连续无框采样数为v13的16、v14的1、v15 last的8；没有逐帧完整真值，不能换算成火焰召回、真实漏检时长或报警延迟。视频6起始视角均无框，是否存在清楚可见火焰没有作真值判定。

## 本阶段取舍及继续路线

优先推进 **v14 last的锅底蓝焰电脑端运行候选**：实际视频收益较明确，参数仍为9428179；best/last的视频主要表现接近，last旧无火FP略少。接受其旧图AP/召回代价进入后续项目验证，不将它宣称为所有场景通用替代。v13保持可回退且保持已有smoke组合；v14特征已变，不能直接套用依赖v3/v13固定特征的smoke头。v15 last保留作框口径修正研究，当前仍有大锅体框和重复框。

v14 last已单独动态ONNX导出，80/80张开发诊断的预处理、原始输出和最终NMS一致性通过；输入策略为stride32矩形，阈值及数值容差未放宽。权重SHA256 `a46690756e65826060392688e98ceb268c9ecfa3f007e5796fa3c38ef4b5833e`；ONNX SHA256 `b0b7a7fd7aa0c44b70aea20528fa2ad94369dc49de2a11928612a27917b83762`。已实际运行独立CPU图片入口和视频7入口，不依赖Torch/Ultralytics推理；运行详细计数另存本地及后续运行汇总。该动态产物不等于K230静态/量化模型。

独立CPU视频入口完整解码734帧（元数据差0），27个采样中24帧有框、共33框，与GPU这段的计数一致；未以计数相同代替逐框数值比较。平均ONNX前向58.23ms仅为该机器当次运行测量，不含完整端到端报警或板端能力。独立图片入口的叠加图已实际查看，框落在锅底蓝焰，食物和贴纸未画框。见 [运行身份与计数](../../docs/fire_scratch_v14_pc_runtime_20261002.json)。

下一轮重点补齐物理火焰标签的一致性，并评估从v14已学到的小蓝焰特征继续适配的收益；训练前另立编号、数据身份与固定日程。先检查关火、食物、烹饪羽流及连续火焰定位，避免只追求已曝光照片分数。独立厨房、两类F1、长时误报警和板端性能仍待验证。
