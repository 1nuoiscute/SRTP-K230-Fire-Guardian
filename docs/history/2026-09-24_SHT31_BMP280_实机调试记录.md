## 2. 2026-09-24 排查时的实测事实

用户提供的 Bosch 手册第 24 页直接给出 `0xD0` 的固定芯片 ID `0x58`；第 28–29 页给出 `SDO=GND` 时 7 位地址 `0x76`、`SDO=VDDIO` 时为 `0x77`，并说明 `CSB` 必须接高电平才能启用 I²C；若上电过程中 `CSB` 曾被拉低，器件会锁定为 SPI 模式，直到下一次完整断电重启。第 29 页还确认读寄存器时先写寄存器地址，再以 STOP 或 repeated START 切换为读。第 35、38 页给出芯片引脚定义及推荐 I²C 接线。后续要检查实物的 `CSB/SDO`，但不能从旧版扩展板图纸直接假定其电压。

## 3. 引脚切换、复原与当时板端状态

K230 IOMUX 寄存器基址 `0x91105000`，每脚 4 字节。根据芯片 IOMUX 功能表，`GPIO44/45` 的 `alt2` 是 I²C3；原固件将 I²C3 设在 `GPIO36/37` 的 `alt1`。测试时经 COM6 的 `devmem2` 暂时设置：

```text
GPIO36 0x91105090: 0x9CF  -> 0x1CF
GPIO37 0x91105094: 0x9CF  -> 0x1CF
GPIO44 0x911050B0: 0x1CF -> 0x11CF
GPIO45 0x911050B4: 0x1CF -> 0x11CF
```

随后仅测试 BMP280 两个可能地址及寄存器 `0xD0`。测试后**四脚全部恢复原值**，串口写后读回确认；Linux 小核再次读到 `GPIO44/45 = 0x800001CF`。临时弱下拉试验也已恢复。这些改动均是内存寄存器操作，没有写入固件或启动配置。

本记录写入时，视觉程序已退出到 `msh />` 以做传感器测试；屏幕可能因此黑屏。恢复视觉 MVP 使用：

```sh
cd /sharefs/srtp_clean/vendor_ob_det
ob_det_fire_mvp_spaces.elf best_vendor80_640.kmodel 0.5 0.6 None 1
```

摄像头程序运行时需输入 `q` 加回车退出。下一次测试前先确认串口/ADB 和板上当前进程，不要假定本节状态仍然实时有效。

## 4. 当时拟定的执行顺序与通过标准（已完成部分见第 0 节）

1. **先只调 BMP280。** 从用户提供的扫描手册选读 I²C 地址、`0xD0` ID 和总线时序页；核对 Bosch 数据手册和板上实际焊接方向。确认 SCL/SDA 静态电平及板上上拉位置，不移动黄色跳线。
2. 已清除 I²C3 旧 `TX_ABRT`，`i2c_write 3 0x76 0xF4 0x27`（单消息）与 `i2c_read 3 0x76 0xD0`（写后读）均重新触发 `0x00801000` 仲裁丢失。现阶段先解决 SCL/SDA 相互牵连，再重试硬件 I²C；单独写命令虽未打印失败，但驱动源码中的发送完成路径未检查 `TX_ABRT`，不能算写成功。
3. **已找到原跳帽接法造成的短接，待通电复测。** 用户指出两只跳帽都搭在 `4.7` 档；放大核对 `D:\111\01_学习手册\k230-副板.pdf` 中 P2：第 9、10 脚直接相连，SCL 与 SDA 各自跳到这两个脚时会被直接连在一起。用户断电取下最右下角两只黄色跳帽后，在扩展板 SCL–SDA 测得不再导通。已指导将上排 SDA 跳帽从 `SDA–4.7` 左移一格至 `2.2–SDA`，下排 SCL 保持 `SCL–4.7`，使两线选择不同电阻节点；目前等用户装好、通电后复测 GPIO 独立性和 BMP280 ID。**不要在通电状态下移动扩展板或跳线。**
4. BMP280 的最小通过标准：在 `0x76` 或 `0x77` 连续 3 次读 `0xD0` 都为 `0x58`，随后读出温度原始寄存器及校准参数并换算出合理温度；只读到上拉高电平或仅有 3.3 V 不算通过。
5. BMP280 通过后再定位 SHT31 供电：复核万用表落点，测 SHT31 去耦电容 C14 两端相对 GND 的电压，确认芯片 VDD/GND。然后读 `0x44` 或 `0x45` 并做一次温湿度采样与 CRC 校验。AHT20 现阶段不参与测试。

### 诊断程序说明

`src/sensor_debug/bmp280_gpio_probe.c` 是一次性 GPIO 模拟 I²C 对照程序，Linux 小核运行，源码和编译产物分别在 `<PROJECT_ROOT>\src\sensor_debug\` 与 `artifacts\sensor_validation\bmp280_gpio_probe`。它对 `0x76/0x77` 只尝试读 `0xD0`，退出时恢复引脚。用 **Linux glibc 交叉编译器**生成的版本已启动；结果为释放 SCL 后仍低，未进入地址应答阶段。独立寄存器测试随后证实：拉低任一线会把另一线同时拉低。最初误用 RT-Smart musl 工具链生成的 ELF 入口为 `0x0`，曾在 Linux 小核启动时段错误；该无效产物已被正确链接版本替换，不能把那次程序错误当作传感器故障。
