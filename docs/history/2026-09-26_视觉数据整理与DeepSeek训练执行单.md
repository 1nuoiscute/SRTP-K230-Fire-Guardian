## 3. 数据整理口径，按顺序执行

### 3.1 先审图，后映射

至少分层查看新灶火原图：类 0 反光、类 1 锅下火、类 2 裸露灶火、类 3 未点火炉位，以及很小的蓝焰、强反光、锅遮挡、无火但高亮、多人/多灶画面。按源图组抽样，不要只看增强版本。保存抽样文件路径、原标签与判读结果；发现混标时记录比例和具体例图，必要时停止自动合并并修订规则。

统一目标检测标注规则：

| 输入来源标签 | 目标四槽处理 | 理由 |
| --- | --- | --- |
| gc `1 flame-under-pot`、`2 gas-stove-flame` | 暂定映射 `fire=0`，人工抽检确认后执行 | 受控火苗同样应被检测；危险性质由时间/上下文层判断 |
| gc `0 flame-reflection` | 不生成 `fire` 框，作为困难负例区域；保留同图其他真实火框 | 防止金属/玻璃反光报火；抽检若发现真实火误标为反光，先修源图派生标签 |
| gc `3 no-flame` | **不映射到 `stove`**，仅移除这个框；若该图没有其他有效框，则成为空标签负例 | 该框是未点火炉位，不等于旧 `stove` 数据中“整个灶具”框 |
| old fire-flame `0 fire` | `fire=0`；先按组去重和筛选，再限制其训练占比 | 只代表通用可见火，不代表异常报警 |
| stove-detection `0 stove` | `stove=2`，少量抽图确认灶具框范围 | 原 YAML 为单类 stove |
| pan-detection `1 Pan` | `pan=3`，少量抽图确认；`0 Black Circle` 丢弃 | 原 YAML 类 0 不是锅，不能按 0→pan |
| Home-fire 原类别 0/1 | **暂缓**；先取得官方类名与人工抽检 | 不可凭 ID 猜火/烟 |
| 厨房旧 64 图 | 全部暂缓，逐张重标且核版权 | 有空标、伪标、图库素材和场景名误导 |

负例若画面中存在未框出的真实火苗，不能当作负例；应补框或弃图。允许同图有多个灶火框。真实火焰框围住可见火舌，不把锅体、炉架、高光整片框进去。**`no-flame` 不是一个要保留给四槽模型的新类别。**

已按上述拟定映射做**只读计数**：gc 的 `1+2→fire` 后，train/valid/test 分别有 **3,284 / 468 / 234 个 fire 框**，**空标签图片均为 0**；分别有 **762 / 215 / 109 个带 fire 的源图组**。因此审查提出的“删去反光和 no-flame 会产生大量整图负例”在**这份 v2 数据上不成立**：每张 GC 图同时至少有一个真实火框。它提供局部反光/未点火炉位对照，却**不提供纯无火整图**。DeepSeek 必须另找并核准纯无火厨房难例，按地点/场景分组纳入，且在构建后的统计表中重新计算上述数字；不要把旧 64 图里有图库权利疑问的 `no_fire` 自动加入。

### 3.2 划分与构建

在 `model_work/src/` 写新的可复跑构建脚本，输入原目录只读，输出建议 `D:\SRTP_Datasets\kitchen_vision_v2_20260926`（先检查不存在；若已存在，用下一个版本目录）。输出 `data.yaml`、每张图片的来源清单、原 SHA-256、源图组 ID、许可、原/新类别、场景审核状态、划分、所有排除理由。脚本**拒绝覆盖**，不能删除原始文件。

**首轮正式验证仅报告**：正常灶火（小蓝焰/锅下分项）和无火反光/灯光/蒸汽难例的检出、漏检、误报；逐项列出图片数、源图组数、独立拍摄场景数。异常厨房火、爆炒时间状态列在“缺失数据/未验收”，不以该 GC 集给出准确率。按**视频/场景组**计误报和漏检，保存逐图结果。单帧不能判爆炒或异常，视频状态测试应另行构建。

### 3.3 构建完必须自动验收

逐张图能解码；每张标签存在（可为空）；类 ID 只在 0–3；框坐标合法且在图内；图/标签数一致；无源组、SHA-256 相同图、感知近重复图跨 train/val/test；val/test 无增强复制；数据 YAML 的绝对路径可被训练环境读到。用随机抽样可视化每一类框和空标签负例，人工签收至少几十张关键难例。产出 JSON/CSV 审计报告和数据 YAML 哈希。任何不合格项先修复再训练。

## 7. 2026-09-26 对 DeepSeek“数据泄漏”结论的独立复核

复核对象为**原始** `D:\gc_kitchen_annotation.v2-version_two.yolov11`，没有改动原图、标签或 DeepSeek 构建的数据集。只读复核脚本：`<PROJECT_ROOT>\model_work\src\independent_gc_leak_check.py`。它重新计算每张图的 64 位 dHash，并对 dHash 完全相同的跨 split 配对计算缩放至 256×256 后的 RGB 像素平均绝对差（MAE）；结果没有直接采用 DeepSeek 的泄漏报告。

| 原始评测集 | 图数 | 与原 train 的最小 dHash 距离 = 0 | 距离 ≤ 4 |
| --- | ---: | ---: | ---: |
| valid | 215 | 99 | 187 |
| test | 109 | 50 | 92 |
| 合计 | **324** | **149（46.0%）** | **279（86.1%）** |

这证明原始 GC 划分存在**严重的视觉重叠风险**，其 valid/test 不可直接用于声称独立场景精度。它**不证明 149 张都是同一张照片的复制品**：dHash=0 的 149 个最佳配对中，104 个的像素 MAE≤3、121 个≤5，仍有部分差异较大。人工抽看 `valid/DSC_6345...` 与 `train/DSC_6341...`：同一机位、不同火焰瞬间，MAE≈19.1，但 dHash=0；`valid/DSC_4956...` 与 `train/DSC_4952...` 则几乎相同（MAE≈0.67）。因此应表述为“重复或高度相似的相邻帧/场景混入训练和评测”，不要将哈希相等直接改写成“完全相同照片”。

DeepSeek 重切后的 `D:\SRTP_Datasets\kitchen_vision_v2_20260926\manifest.csv` 经独立计数，GC 图为 train **1,807**、val **27**、test **14**。27/14 是该脚本按 dHash≤4 组成视觉族之后留下的**图数**，不是已验证的独立厨房/事件数；阈值也可能合并相似但不同的照片，不能把它当作唯一正确切法或“最多只能留这些”。原始文件名前缀和 SHA-256 检查未抓到这类跨 split 重叠，今后须按拍摄地点/视频段分组并人工核查边界案例。

**后续口径**：可以在这版数据上训练探索性模型，用于检查小蓝焰/锅下火识别是否有改善；不能依据现有 GC valid/test 给出可信的正式精度，也不能因一次小样本 mAP 就推进板端替换。先补不同厨房、不同时间与机位的独立灶火和纯无火难例，并把这批新样本冻结为测试集；验证集用于选阈值，测试集最后只评一次。DeepSeek 报告中的“formal 66/58”也只表示数据来源分层，**不等于已经通过独立场景验收**。烟雾、爆炒、异常厨房火仍分别缺少相应真值，单轮灶火检测训练不能证明这些能力。
