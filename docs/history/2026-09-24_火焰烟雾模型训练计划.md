## 1. 先做数据审计和标注，不急着开训

现有 `datasets\combined\data.yaml` 的抽查结果：训练 10,693 图、验证 6,738 图；`smoke` 框数均为 **0**；`_dN` 复制图分别 3,396、3,660 张。原始来源主要在 `datasets\fire-flame.v1i.yolov11`、`stove-detection`、`pan-detection` 和 `kitchen-images`。其中 `kitchen-images` 约 64 张已标注或空标注图片，部分由旧模型伪标，需人工复查。另有 `datasets\hiennguyen9874_fire-smoke-detection` 原始数据目录/Parquet，**尚未核实类别映射、标签质量、许可与转换方式**；先审计，别直接混入训练集。

DSH 先生成只读清单：每个来源的图片数、标签数、类别框数、空标签数、无法打开/越界框、原图组别、重复/近重复，以及授权说明。保存成版本化 CSV/Markdown。对相同视频连续帧、同一源图的裁剪/增强图，赋同一 `group_id`。先按组切分，再做任何复制或增强；同组不得跨 train/val/test。保留原始数据不改，**新数据只写** `<USER_HOME>\Documents\Codex\kitchen-fire-detection\datasets\combined_v2\`。

### 标注口径

| 类别 | 该标什么 | 特别检查 |
| --- | --- | --- |
| `fire=0` | 可见的真实火苗/明火区域，框住可辨火焰 | 亮灯、LED、反光、夕阳、蒸汽亮斑、屏幕中的火焰画面作为专门的难负例复核；若产品目标也包含屏幕中的火，先明确需求再标 |
| `smoke=1` | 可见烟团/烟柱，边界可辨时标框 | 与水蒸气、雾、油烟、云和曝光伪影区分；没有足够人工复核的正例前，不能声称可检烟 |
| `stove=2` | 灶具主体 | 与火焰框独立；不要把炉面反光标成火 |
| `pan=3` | 锅具 | 统一锅边界、被遮挡时的标注规则 |

无目标图可用空 `.txt` 标签；不能把漏标的火/烟图当负样本。优先补现场摄像头同视角样本：真实明火、正常做饭、灶台高光、LED/屏幕亮斑、蒸汽/油烟、无火厨房、昼夜与不同曝光。第 17 节的高亮误报图要收为回归样例，但评测图与训练图必须分开；不能一边用它调模型一边把它报为独立测试成绩。

### 新数据集结构和检查

```text
<USER_HOME>\Documents\Codex\kitchen-fire-detection\datasets\combined_v2\
  data.yaml
  images\train\   images\val\   images\test\
  labels\train\   labels\val\   labels\test\

```

`data.yaml` 保持四类顺序，示例（创建目录后再使用）：

```yaml

train: images/train
val: images/val
test: images/test
names:
  0: fire
  1: smoke
  2: stove
  3: pan
```

YOLO 检测标签每行 `class x_center y_center width height`，后四列是 0–1 归一化值。建集后自动校验：图像能解码、每图标签匹配、类别 ID 属于 0–3、框宽高正值且框不越界、没有跨 split 的同源组和相同/近似图片。`val/test` 不做 `_dN` 复制；仅在 train 阶段用在线增强或经过记录的重采样。烟雾正例不足时保留四类接口，但将 smoke 标记为“未训练/不验收”，不要编造逐类指标。

## 2. 基线评测与第一轮训练

先冻结 `combined_v2` 的 `test`，记录 manifest 哈希。用**同一 test 集**对旧 `best.pt` 做基线评测：逐类 precision、recall、mAP50、mAP50-95；另对按场景分类的视频/图片统计火焰漏检和每段负例中的误报。报告检测阈值，旧板端当前命令为置信度 `0.5`、NMS `0.6`；评测阈值要单独记录，不能只比较默认 mAP。

第一轮继续用已有 YOLO11s `best.pt` 微调，输入 640，与当前能上板的接口一致。新输出目录定为 `<USER_HOME>\Documents\Codex\kitchen-fire-detection\runs\kitchen-fire-v2-640`。下面命令在 **PowerShell**、新数据集审核通过后执行；`batch=4` 是 8 GB 显存的保守起点，若 OOM 改为 2 并在日志注明，训练前确认输出目录不存在：

```powershell
& '<USER_HOME>\miniconda3\python.exe' -c 'from ultralytics import YOLO; m=YOLO(r"<USER_HOME>\Documents\Codex\kitchen-fire-detection\runs\kitchen-fire\weights\best.pt"); m.train(data=r"<USER_HOME>\Documents\Codex\kitchen-fire-detection\datasets\combined_v2\data.yaml", epochs=100, patience=25, imgsz=640, batch=4, device=0, workers=0, seed=20260924, project=r"<USER_HOME>\Documents\Codex\kitchen-fire-detection\runs", name="kitchen-fire-v2-640", exist_ok=False, save=True, plots=True)'
```

这表示从旧权重**开始新训练**，不是 `resume=True` 续训旧 run。若中断，先核对新 run 的 `last.pt` 和 `args.yaml`，只对这个新 run 使用 `resume=True`；不要用原 `train.py` 重启。保存实际安装版本、命令、随机种子、`data.yaml`、manifest、`best.pt/last.pt` 哈希、`results.csv` 和关键失败日志。`optimizer/增强`先沿用库当前默认值并保留 `args.yaml`，不要在一次对比中同时更换数据、模型大小、输入尺寸和阈值。

训练后分别在冻结的 `val` 调阈值，在 **test 仅做最终一次确认**；对基线和新模型用相同图片与阈值比较。若 `smoke` 已有足够经审核正例，单独报 smoke 的 P/R、误检和漏检；否则仍标“未验收”。收集主要误报与漏检各若干例，按来源、光线、场景、尺度归因，决定第二轮补数。

## 4. 板端对照验收和回滚

板端仅余约 4.1 MB，推新版前先确认空间、备份并核对 SHA-256；**不要覆盖** `/bin/fastboot_app.elf`、`/bin/test.kmodel`、`/bin/init.sh`、原厂 ELF/KModel 或现有 `board_mvp_640` 的电脑副本。建议板端新目录/新文件名，旧 MVP 始终可回滚。若空间不够，仅删除已备份且不在运行的旧实验文件，先记录被删的完整路径与哈希。

验收顺序：单图测试集样本 → 摄像头实时画面与 `fire` 框 → 至少一段有火、一段无火/高亮干扰视频 → 持续运行和 `q` 退出。每次保存命令、串口日志、屏幕照片、输出图、模型/ELF 哈希、帧率和失败现象。第一轮建议的**候选通过条件**：独立 test 的 fire 召回不低于基线、目标难负例误报下降、板端 10 分钟无异常且帧率不低于 3 fps；如果达不到，保留当前 MVP 并继续补数/调参。烟雾检测单独设验收门槛，不随火焰通过自动通过。
